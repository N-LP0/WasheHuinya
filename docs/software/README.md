# WasheHuinya HID MacroPad

ESP32-S3 устройство для HID-автоматизации. HID-события отправляются по USB или Bluetooth LE, а управление выполняется по Wi-Fi через web UI, HTTP API и TTY-команды.

![HIDPad Control](<HIDPad Control.png>)

## Быстрый старт

1. Подключи ESP32-S3 по USB для питания и прошивки. В USB HID-режиме этот компьютер также будет получать HID-события.
2. Подключись к Wi-Fi точке доступа устройства.
3. Открой web UI:

    ```text
    http://192.168.4.1
    ```

    Если устройство подключилось к твоей Wi-Fi сети, можно открыть:

    ```text
    http://hidpad-s3.local
    ```

    mDNS поддерживается не во всех сетях и ОС. Вместо имени можно использовать STA IP, выданный роутером и показанный в Web UI или списке DHCP-клиентов, например `http://192.168.55.45`.

4. На вкладке `Wi-Fi` задай SSID и пароль сети.
5. На вкладке `HID / BLE` выбери транспорт. Для USB используется единый тип `Keyboard + mouse`; для BLE выбери `Keyboard` или `Mouse`.
6. На вкладке `Settings` задай hostname, профиль по умолчанию и TTY-пароль.
7. На вкладке `Control` открой или создай макрос.
8. Нажми `Test`, чтобы запустить текст из редактора без сохранения.
9. Нажми `Save`, чтобы сохранить макрос в профиль.
10. Нажми `Run saved`, чтобы запустить выбранный сохраненный профиль.

В USB-режиме доступны клавиатурные и мышиные команды одновременно. В BLE-режиме устройство работает только в выбранной роли: `Keyboard` принимает команды `TEXT`/`KEY`, а `Mouse` принимает команды `MOUSE`.

## Web UI

Интерфейс разделен на вкладки `Control`, `TTY`, `GPIO`, `Wi-Fi`, `HID / BLE`, `Settings`, `Observe` и `Update`.

### Control

В верхней строке состояния постоянно отображаются AP, STA, активный HID-режим и состояние макроса. Возможные значения HID-режима: `USB keyboard + mouse`, `BLE keyboard` и `BLE mouse`.

На вкладке управления доступны:

- статус AP/STA, IP-адреса и состояние макроса;
- список сохраненных профилей;
- редактор макросов с номерами строк и подсветкой команд;
- локальная проверка синтаксиса перед сохранением и запуском;
- автодополнение команд и ключевых слов в редакторе;
- модальное окно справки по синтаксису макросов;
- повторы и бесконечные циклы внутри текста макроса через `REPEAT`, `LOOP` и `END`;
- `Test` для запуска текущего текста из textarea без сохранения;
- `Save` для сохранения профиля;
- `Run saved` для запуска выбранного сохраненного профиля;
- `Export` для скачивания всех профилей одним JSON-файлом;
- `Import` для загрузки профилей из JSON-файла;
- `Stop` для остановки выполняющегося макроса.

Разделение `Test` и `Run saved` сделано намеренно. `Test` удобен для отладки макроса перед сохранением, а сохраненные профили можно запускать из web UI, TTY и GPIO-кнопок.

Имена профилей валидируются до сохранения. Допустимы только латинские буквы, цифры, `_` и `-`; пробелы не допускаются.

### TTY

На вкладке TTY доступны:

- поле `Access token` для TTY-аутентификации;
- отправка TTY-команды;
- модальное окно справки по TTY-командам;
- TTY-лог в реальном времени через WebSocket;
- явный индикатор состояния WebSocket-соединения;
- фильтры уровней TTY-лога `INFO`, `WARN`, `ERROR` над окном `TTY log stream`.

Подробности описаны в [TTY.md](TTY.md).

### GPIO

На вкладке GPIO можно назначить сохраненный профиль на физическую кнопку.
Системная команда `STOP` всегда присутствует в назначениях GPIO, по умолчанию стоит на `GPIO4`, может быть переназначена на другой разрешенный пин и не удаляется из `Assigned GPIO`.

Кнопка подключается между выбранным GPIO и `GND`. Прошивка использует внутреннюю подтяжку `INPUT_PULLUP`, прерывания и антидребезг.

GPIO-кнопки работают по удержанию:

- нажал кнопку: назначенный профиль запускается;
- пока кнопка удерживается, профиль повторяется;
- отпустил кнопку: макрос доходит до последней строки текущего прохода и завершается;
- нажал вторую кнопку, не отпуская первую: вторая кнопка выигрывает, первый макрос останавливается сразу.

Допустимые пины и электрическое подключение описаны в [GPIO.md](GPIO.md).

### Wi-Fi

На вкладке Wi-Fi доступны:

- SSID и пароль внешней Wi-Fi сети;
- сброс сохраненных SSID и пароля кнопкой `Reset Wi-Fi`;
- диагностический статус подключения к роутеру.

SSID может содержать пробелы.

AP используется как setup/fallback-режим. Если SSID и пароль не сохранены или подключение к роутеру не установлено, устройство поднимает точку доступа и captive portal. Если SSID сохранен, устройство продолжает переподключаться к STA по таймеру даже при активном AP. Попытки прекращаются только после `Reset Wi-Fi`, который очищает сохраненные SSID и пароль. После успешного подключения к внешней Wi-Fi сети AP выключается.

Текущая логика Wi-Fi:

- SSID сохранен: устройство всегда пытается переподключиться к STA каждые `15s`;
- STA не подключена: AP и captive portal остаются доступными как fallback;
- STA подключилась: AP выключается;
- связь потерялась: AP снова поднимается, STA reconnect продолжается;
- `Reset Wi-Fi`: очищает SSID/password, после этого STA-попытки прекращаются и остается setup AP.

В режиме AP устройство поднимает точку доступа:

- SSID: `HIDPad-Setup`;
- пароль: `hidpad1234`;
- адрес web UI: `http://192.168.4.1`.

Captive portal перенаправляет стандартные проверки подключения ОС на web UI устройства.

### Settings

На вкладке Settings доступны:

- hostname устройства;
- профиль по умолчанию из выпадающего списка сохраненных профилей;
- TTY password;
- отключение TTY-аутентификации;
- текущие значения настроек устройства.

### HID / BLE

На вкладке HID / BLE доступны:

- выбор транспорта `USB` или `Bluetooth LE`;
- единственный USB-тип `Keyboard + mouse`;
- выбор BLE-роли `Keyboard` или `Mouse`;
- имя BLE-устройства: `HIDPad S3 keyboard` или `HIDPad S3 mouse`;
- состояние BLE pairing/connection;
- список сохраненных BLE bonds;
- удаление отдельного bond по Bluetooth-адресу;
- сброс всех сохраненных сопряжений.

Сохранение настроек перезагружает устройство. Для первого подключения выбери устройство с заданным Bluetooth-именем в настройках ОС. Pairing/bonding выполняется средствами BLE. При смене роли клавиатура/мышь удали старое сопряжение на компьютере и подключи устройство заново, поскольку ОС может кэшировать имя, PnP ID и HID descriptor.

Прошивка публикует отдельные BLE PnP product ID для клавиатуры и мыши. Если Windows продолжает показывать старое имя после обновления прошивки, удали устройство в Bluetooth-настройках и Device Manager, затем выполни сопряжение заново.

Удаление bond в web UI очищает ключи только на ESP32-S3. Соответствующее устройство также нужно удалить на компьютере или телефоне, иначе хост может продолжить использовать старые ключи. Управление bonds доступно только при активном транспорте `Bluetooth LE`.

RGB-светодиод быстро мигает голубым во время pairing и постоянно горит голубым при активном BLE-подключении. Полная таблица состояний приведена в [LED.md](LED.md).

USB-кабель можно оставить подключенным для питания: USB не использует радиоканал и не конфликтует с Wi-Fi/BLE. В BLE-режиме макросы отправляют HID-события только через Bluetooth. Wi-Fi и BLE используют общий радиомодуль ESP32-S3; прошивка включает сбалансированный coexistence-режим для их одновременной работы.

### Observe

На вкладке Observe доступны:

- версия прошивки;
- дата и время сборки;
- uptime с момента загрузки;
- модель чипа, ревизия, частота CPU и версия SDK;
- состояние heap, размер flash, размер текущего sketch и свободное место OTA;
- состояние LittleFS, количество профилей и GPIO-привязок;
- hostname, Wi-Fi состояние, IP-адреса, RSSI и канал;
- активный HID-транспорт, BLE-роль, BLE-состояние и количество сохраненных bonds;
- счетчик ошибок API;
- счетчик попыток Wi-Fi reconnect;
- счетчик запусков макросов;
- текущие выбранные уровни TTY-лога: `INFO`, `WARN`, `ERROR`.

Счетчики хранятся в RAM и сбрасываются при перезагрузке устройства.

Версия прошивки задается в корневом `platformio.ini` через build flag `HIDPAD_FIRMWARE_VERSION`. Текущая версия: `0.5.1`.

### Update

На вкладке Update можно загрузить новую прошивку и новый LittleFS-образ через web UI одной сессией:

- `Firmware image` принимает `firmware.bin`;
- `Filesystem update` принимает `littlefs.bin`;
- кнопка `Update firmware + filesystem` сначала загружает прошивку, затем LittleFS;
- после успешной загрузки обоих файлов устройство перезагружается.

Подробности описаны в [FIRMWARE_UPDATE.md](FIRMWARE_UPDATE.md).

Hostname и профиль по умолчанию используют те же правила имен: латинские буквы, цифры, `_` и `-`, без пробелов.

## Макросы

Профиль макроса - это текстовый сценарий.

Поддерживаются команды:

```text
TEXT <text>
TYPE <text>
DELAY <ms>
WAIT <ms>
KEY <key or modifiers>
HOTKEY <key or modifiers>
MOUSE MOVE <x> <y> [jitter]
MOUSE WHEEL <delta>
MOUSE SCROLL <delta>
MOUSE PAN <delta>
MOUSE HWHEEL <delta>
MOUSE CLICK <button>
MOUSE PRESS <button>
MOUSE RELEASE <button>
RELEASEALL
```

`MOUSE MOVE` отправляет относительное HID-смещение. Прошивка заранее рассчитывает HID-шаги с компенсацией типичного pointer acceleration/ballistics: сырые report-ы крупнее в начале движения и постепенно уменьшаются к концу. Это помогает визуально выровнять скорость длинных перемещений вроде `MOUSE MOVE 320 0`, когда ОС разгоняет указатель по мере накопления быстрых report-ов. Необязательный параметр `jitter` задает высоту плавной дуги: `MOUSE MOVE 120 0 3` идет с компенсированной скоростью по X, но проходит по небольшой дуге по Y. Итоговая сумма HID-смещений останется `120,0`. Допустимый диапазон ограничивается прошивкой до `0..12`; практичные значения - `1..4`.

Если курсор упирается в край экрана или ОС/приложение дополнительно меняет чувствительность мыши, абсолютный возврат в исходный пиксель всё равно не гарантируется.

`MOUSE WHEEL`, `MOUSE SCROLL`, `MOUSE PAN` и `MOUSE HWHEEL` также дробятся на единичные события с паузой между report-ами. Это снижает эффект ускорения прокрутки в ОС: `MOUSE WHEEL -5` ведет себя ближе к пяти отдельным щелчкам колеса, а не к одному крупному импульсу.

Комментарии в макросах:

```text
# комментарий
; комментарий
// комментарий
```

Комментарии игнорируются при выполнении, но остаются в тексте профиля. Импорт и экспорт профилей сохраняют такие строки вместе с остальным `script`.

Для клика по колесу используй:

```text
MOUSE CLICK MIDDLE
MOUSE CLICK WHEEL
MOUSE CLICK MBUTTON
```

Пример:

```text
KEY CTRL ALT T
DELAY 300
TEXT git status
KEY ENTER
```

Повторы задаются в тексте макроса, а не в кнопке запуска:

```text
REPEAT 40
  MOUSE MOVE 340 0 4
  DELAY 120
  MOUSE MOVE 0 -340 4
  DELAY 120
  MOUSE MOVE -340 0 4
  DELAY 120
  MOUSE MOVE 0 340 4
  DELAY 120
END
```

`LOOP ... END` выполняет блок бесконечно до кнопки `Stop`, TTY-команды `STOP` или GPIO-команды `STOP`.

Готовые примеры лежат в [`data/profiles`](../../data/profiles) и попадают на устройство при загрузке LittleFS:

- `hello` - печатает короткое сообщение;
- `terminal` - открывает терминал и печатает тестовое сообщение;
- `mouse_test` - двигает курсор небольшим квадратом;
- `scroll_test` - проверяет колесо мыши и клик по колесу.
- `update_f5` - нажимает `CTRL+F5` и ждет 60 секунд.

Прошивка не создает профили автоматически при загрузке. Если удалить все профили через web UI, список останется пустым после перезагрузки. Примеры появятся снова только при повторной загрузке LittleFS-образа, в котором есть файлы из [`data/profiles`](../../data/profiles).

`Default profile` на вкладке `Settings` необязателен и выбирается из списка сохраненных профилей. Значение `None` означает, что профиль по умолчанию не задан. Если профиль по умолчанию пустой или удален, запуск без явного имени профиля вернет ошибку, но новый `admin` создан не будет.

## TTY-доступ

TTY в этом проекте - это командный интерфейс по Wi-Fi, а не обязательно Linux-устройство `/dev/tty*`.

Поддерживаемые команды:

```text
HELP
PING
RUN <profile>
STOP
LINE <macro_line>
```

Примеры:

```text
RUN hello
RUN mouse_test
STOP
LINE KEY CTRL ALT T
LINE TEXT git status
LINE KEY ENTER
```

Подробная настройка Linux, USB/BLE HID, режима прошивки, TTY auth и WebSocket-лога описана в [TTY.md](TTY.md).

## HTTP API

API описан в [openapi.yaml](openapi.yaml).

Основные endpoint-ы:

```text
GET  /api/status
GET  /api/ping
GET  /api/observability
GET  /api/profile/load?name=...
POST /api/profile/save
GET  /api/profile/export
POST /api/profile/import
POST /api/profile/delete
POST /api/run
POST /api/run/script
POST /api/stop
POST /api/wifi/save
POST /api/wifi/reset
POST /api/ble/save
POST /api/ble/bond/delete
POST /api/ble/bonds/clear
POST /api/gpio/save
POST /api/gpio/delete
POST /api/tty/exec
GET  /api/tty/log
POST /api/update/firmware
POST /api/update/filesystem
GET  /api/update/progress
```

`POST /api/run` запускает сохраненный профиль.

`POST /api/run/script` запускает переданный текст макроса без сохранения. Этот endpoint используется кнопкой `Test`.

Ошибки API возвращаются в едином JSON-формате:

```json
{
  "error": {
    "code": "profile_not_found",
    "message": "Profile was not found"
  }
}
```

Успешные ответы возвращаются в JSON-формате:

```json
{"ok":true}
```

Если endpoint возвращает данные, они находятся в поле `data`.

## LED-индикация

На плате установлен WS2812 RGB-светодиод на `GPIO21`.

Светодиод показывает состояние загрузки, Wi-Fi, выполнения макроса и ошибки. Цвета намеренно очень тусклые, чтобы не слепить и не добавлять заметный нагрев.

Подробности описаны в [LED.md](LED.md).

## Сборка и прошивка

Команды выполняются из корня репозитория. Проект собирается через PlatformIO. Основная среда:

```ini
default_envs = esp32s3zero
```

Проверка сборки:

```powershell
pio run -e esp32s3zero
```

Сборка LittleFS-образа:

```powershell
pio run -e esp32s3zero -t buildfs
```

После изменения C++ кода нужно загрузить прошивку. После изменения файлов в [`data`](../../data) нужно загрузить LittleFS image.

В PlatformIO обычно нужны задачи:

- `Upload` - загрузка прошивки;
- `Upload Filesystem Image` - загрузка LittleFS.

COM-порты в `platformio.ini` не зафиксированы, PlatformIO должен определять порт автоматически.
